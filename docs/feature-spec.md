## 3. 업무 규칙

### 일정 상태

| 상태 | 조건 | 화면 |
| --- | --- | --- |
| `NOT_OPEN` 오픈 전 | 현재 시각 < 예약 오픈 시각 | 예약 버튼 없음 |
| `OPEN` 예약 가능 | 오픈 이후, 잔여 정원 있음, 치료일 전날까지 | 예약 버튼 표시 |
| `FULL` 마감 | 예약 수 = 정원 | 예약 버튼 없음 |
| `ENDED` 종료 | 치료 당일 이후 | 목록에서 "종료" |

- 예약 오픈 시각(`booking_opens_at`)은 일정마다 따로 둡니다. "월 1회 예약 오픈에 요청이 몰린다"는 시나리오를 그대로 재현하기 위해서입니다 📝.
- 시각 판단은 서버 시간대가 아니라 **Asia/Seoul**로 고정했습니다(`petclinic.zone`). 컨테이너는 보통 UTC라서, 고정하지 않으면 오픈 시각이 9시간 어긋납니다.

### 예약 (F4)

| 규칙 | 거절 사유 | 사용자 메시지 |
| --- | --- | --- |
| 오픈 시각 이후에만 예약 가능 | `NOT_OPEN` | 아직 예약이 오픈되지 않은 일정입니다. |
| 치료일 전날까지만 예약 가능 | `ENDED` | 예약하거나 변경할 수 없는 일정입니다. |
| 정원이 차면 마감 | `FULL` | 정원이 마감된 일정입니다. |
| 한 사람은 한 일정에 한 번만 예약 | `DUPLICATE` | 이미 이 일정을 예약하셨습니다. |

- 입력값: 반려동물 이름(필수, 30자 이내), 메모(선택, 255자 이내).
- 마감된 일정이라도 누군가 취소하면 자리가 다시 열립니다.
- 대기열(순번 대기)은 없습니다. 먼저 처리된 요청이 자리를 얻습니다.

### 취소 (F6)와 수정 (F7)

- 취소와 수정은 치료일 전날까지 가능합니다.
- 취소하면 자리가 1개 반환됩니다. 취소한 예약은 목록에 "취소됨"으로 남습니다.
- 취소한 일정을 다시 예약할 수 있습니다. 이때 새 행을 만들지 않고 기존 행을 다시 "예약 완료"로 바꿉니다.
- 수정에서 일정을 바꾸면 기존 일정의 자리를 반환하고 새 일정의 자리를 얻습니다. 새 일정이 마감이면 아무것도 바뀌지 않습니다.

### 계정 (F1)

- 아이디: 영문, 숫자, 밑줄 3~30자. 중복 불가.
- 비밀번호: 8~64자. BCrypt로 해시해 저장합니다.
- 권한은 `USER`(보호자)와 `STAFF`(직원) 두 가지입니다. 가입 화면으로 만든 계정은 모두 `USER`입니다.
- **직원 계정은 환경 변수로 만듭니다.** `PETCLINIC_STAFF_USERNAME`과 `PETCLINIC_STAFF_PASSWORD`를 주면 시작할 때 계정이 없을 경우 만듭니다. 둘 중 하나라도 없으면 만들지 않습니다.
  - 근거: 공개 가입 화면으로 직원 권한을 줄 수는 없고, 기본 비밀번호를 코드나 시드에 넣으면 공개 저장소에 노출됩니다. 쿠버네티스에서는 Secret으로 주입하면 됩니다.
  - 직원 계정을 추가하거나 비밀번호를 바꾸는 화면은 없습니다.

### 관리 화면 (F8)

- 병원: 이름, 지역, 주소, 전화번호를 등록·수정합니다.
- 일정: 병원, 치료명, 치료일, 시작 시각, 정원, 예약 오픈 시각을 등록·수정합니다. 리허설 때 오픈 시각을 여기서 바꿉니다.
- **정원은 이미 예약된 수보다 줄일 수 없습니다.** 수정도 "예약 수 ≤ 새 정원일 때만" 바꾸는 UPDATE 한 문장이라, 수정하는 사이에 예약이 들어와도 초과되지 않습니다 🔍.
- 삭제 기능은 없습니다. 예약이 일정을, 일정이 병원을 참조하고 있어 지우면 예약 내역을 읽을 수 없게 됩니다.

## 4. 정원 마감 처리 방식 (핵심)

**결정: 조건이 붙은 UPDATE 한 문장으로 자리를 얻습니다.**

```sql
UPDATE treatment_schedules
   SET reserved_count = reserved_count + 1
 WHERE id = ? AND reserved_count < capacity
```

- 바뀐 행이 1이면 예약 성공, 0이면 마감입니다. 확인과 증가가 한 문장이라서 DB가 승자를 정합니다.
- 예약 행 저장과 같은 트랜잭션입니다. 중간에 실패하면 자리도 함께 되돌아갑니다.

**근거**

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 잔여 정원을 읽고 → 판단하고 → 저장 | 동시에 읽은 요청들이 모두 "자리 있음"으로 판단해 정원을 넘깁니다 |
| 앱 안의 잠금(`synchronized`) | Pod가 여러 개면 서로 잠금을 모릅니다 📝 EKS에서 여러 Pod로 확장 |
| `SELECT ... FOR UPDATE` | 동작은 하지만 왕복이 한 번 더 필요하고 잠금 유지 시간이 깁니다 |
| Redis 카운터 | 구성 요소가 늘고, DB와 Redis 값이 어긋날 때의 복구 절차가 필요합니다 |

- 이 방식은 **Pod 수와 무관하게** 정원을 지킵니다. 판단을 DB 한 곳에서 하기 때문입니다.
- 🔍 검증: 정원 5인 일정에 40명이 동시에 요청하는 테스트에서 정확히 5명만 성공했고, `reserved_count`와 실제 예약 행 수가 모두 5였습니다(`ReservationServiceTests.manyUsersAtOnceNeverExceedCapacity`, H2 기준).

**추가 안전장치**

- 같은 사용자의 동시 요청(더블 클릭): `(schedule_id, user_id)` 유일 키가 한 건만 통과시킵니다 🔍.
- 취소·재예약·이동도 모두 "현재 상태가 이럴 때만" 바꾸는 조건부 UPDATE입니다. 그래서 취소를 두 번 눌러도 자리가 두 번 반환되지 않습니다 🔍.
- DB에 `CHECK (reserved_count >= 0 AND reserved_count <= capacity)` 제약을 걸었습니다. 앱에 버그가 있어도 DB가 초과를 거절합니다.
- 일정 이동은 두 일정 행을 항상 id 순서로 갱신합니다. 두 사용자가 서로 반대 방향으로 옮길 때 서로의 잠금을 기다리는 상황을 피하기 위해서입니다.

## 5. 로그인과 세션

| 결정 | 근거 |
| --- | --- |
| Spring Security 폼 로그인 | 기준 저장소에 로그인 기능이 없어 새로 추가했습니다 🔍 |
| **세션을 DB에 저장** (Spring Session JDBC) | Pod가 여러 개여도 로그인 상태가 유지됩니다. 또 세션 테이블이 예약 데이터와 같은 DB에 있어서, RDS → Cloud SQL 복제에 함께 실립니다. 그러면 GCP로 전환한 뒤에도 재로그인이 필요 없을 것으로 기대합니다 📝 ⚠️ 실제 전환에서는 미검증 |
| 모든 POST에 CSRF 토큰 필수 | Spring Security 기본값입니다. 기존 PetClinic의 등록 폼 3개에도 토큰을 넣었습니다 |
| Actuator는 `health`, `info`, `prometheus`만 공개 | 원본은 모든 엔드포인트를 열어 두었습니다. 환경 변수 등이 노출되므로 닫았습니다 🔍 `/actuator/env` → 로그인으로 이동 |

**세션 DB 저장의 비용:** 로그인한 요청마다 세션 갱신 쓰기가 생깁니다. 피크(중간 발표 기준 500 RPS)에서 RDS 부하가 얼마나 느는지는 부하 테스트로 확인해야 합니다 ⚠️. 부담이 크면 Redis로 바꿀 수 있지만, 그 경우 전환 후 재로그인이 필요합니다.

## 6. 운영 연동

| 항목 | 내용 |
| --- | --- |
| 헬스체크 | `/actuator/health/liveness`, `/actuator/health/readiness`. 쿠버네티스 프로브와 Route 53 헬스체크 대상 |
| 메트릭 | `/actuator/prometheus` (Micrometer). Prometheus가 수집 |
| 잔여 정원 API | `/api/schedules/{id}/availability`. 화면을 해석하지 않고 마감 여부를 확인할 수 있어 부하 테스트와 상황판에 씁니다 |
| DB 선택 | `SPRING_PROFILES_ACTIVE=mysql`과 `MYSQL_URL`, `MYSQL_USER`, `MYSQL_PASS` 환경 변수 |
| 스키마 생성 | 시작할 때 `db/mysql/schema.sql`, `data.sql`을 실행합니다. 모두 다시 실행해도 안전한 문장입니다 (`IF NOT EXISTS`, `INSERT IGNORE`) |

**부하 테스트(JMeter)에서 달라지는 점**

- POST 전에 화면을 GET해서 `_csrf` 값을 뽑아 함께 보내야 합니다. 세션 쿠키 이름은 `SESSION`입니다.
- 가상 사용자마다 계정이 필요합니다. 테스트 시작 단계에서 `/signup`으로 만들거나, 미리 SQL로 넣습니다.
- 중간 발표의 "방문 등록 p95 3초" 목표는 이제 실제 예약(`POST /reservations`)으로 측정할 수 있습니다.

**구현 방식과 근거**

- **Tailwind를 미리 빌드한 CSS 파일로 넣었습니다** (`static/resources/css/vetcore.css`). Stitch 원본은 브라우저에서 Tailwind를 내려받아 실행하는 방식(`cdn.tailwindcss.com`)인데, 이 방식은 사용자 브라우저가 외부 주소에 접속해야 합니다. 화면이 외부 서비스 상태에 좌우되지 않도록 정적 파일로 바꿨습니다. 다시 빌드하는 방법은 `app/src/main/tailwind/README.md`에 있습니다.
- **글꼴과 아이콘도 외부에서 받지 않습니다.** 아이콘은 원본의 Material Symbols(구글 글꼴) 대신 이미 들어 있는 Font Awesome을 썼습니다. 글꼴은 Plus Jakarta Sans를 지정하되 파일은 넣지 않아, 없으면 시스템 한글 글꼴로 표시됩니다. Plus Jakarta Sans에는 한글이 없어서 한글은 어차피 시스템 글꼴로 나옵니다.
- **기존 보호자·반려동물·수의사 화면은 내용 영역만 예전 Bootstrap 모양**입니다. 상단 메뉴와 색은 새 디자인을 따릅니다.
